## 1. 背景与目标

### 1.1 问题
用 MCP 做麦当劳点餐，全流程需要 20+ 次工具调用、多组中间参数（storeCode / beCode / productCode / couponId / round 结构），人工对话很难稳定走通。

### 1.2 目标
把「4个人吃，不吃辣，其中1人吃素，预算200」这类自然语言，稳定转成一份**满足人数、忌口、预算、并用上优惠券**的可执行订单方案。

### 1.3 非目标
- 不做团餐（beType=6）下单，只做查询
- 不做生日派对 / 主题活动（party 系列）
- 不做积分商城（mall 系列）
- 不做真正的素食主餐 —— **麦当劳菜单没有**，这是客观约束（见 §6）

### 1.4 核心设计原则

| 原则 | 说明 |
|---|---|
| **不静默降级** | 忌口无法满足时必须明确告知，不得默默替换商品 |
| **算价后停下** | 下单涉及真实支付，必须用户明确说"下单"才执行 |
| **一次一券** | MCP 硬限制，多券报 `600022` |
| **数据驱动** | 搭配规则来自接口实测，不靠臆测 |

```
~/.workbuddy/skills/mcd-ordering/          ← skill 本体（运行时依赖）
├── SKILL.md                    ← 触发判定 + 8 步主流程
├── scripts/
│   ├── mcd_call.py             ← 直连封装（权威副本）

├── references/

```

> **改动约定**：`scripts/` 与 `assets/` 的权威副本在 skill 目录，项目内为镜像。改动后两边同步。

### 2.2 调用链路

```
用户一句话
   ↓
[模型] 解析槽位：人数 / 忌口 / 预算 / 场景
   ↓
[脚本] mcd_call.py → JSON-RPC → https://mcp.mcd.cn
   ↓
[模型] 依据 references/dietary.md 决策搭配
   ↓
[脚本] menu_helper.py 计算候选方案与券净省
   ↓
[模型] 呈现方案（含忌口满足情况）→ 停下等确认
   ↓
用户说"下单" → [脚本] create-order → 支付链接
```

### 2.3 为什么必须直连 HTTP

`mcd-mcp` 是 streamable HTTP + JSON-RPC 服务，但平台工具调用层（DeferExecuteTool）会把整型参数降级成字符串：

```
Parameter validation failed: /beType: must be integer;
  /beType: must be equal to one of the allowed values
```

受影响字段：`beType` / `orderType` / `searchType` / `quantity` / `size` 等。

**规避**：所有 MCP 调用一律通过 `scripts/mcd_call.py`，绝不走平台工具层。

该服务**无需 session id**，`initialize` 后可直接 `tools/call`：

```bash
curl -X POST https://mcp.mcd.cn \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"...","arguments":{}}}'
```

### 2.4 编码坑（必须处理）

服务端按 **GBK** 解码请求体。直接发 UTF-8 字节，中文会存成乱码：

| 阶段 | 内容 |
|---|---|
| 发送 | `"无接触配送"` → UTF-8 字节 `e697a0 e68ea5 ...` |
| 存库 | `"޽Ӵ�����"` → U+FFFD 替换字符 |

**规避**：请求体固定 `json.dumps(payload, ensure_ascii=True)`，中文转 `\uXXXX` 纯 ASCII；输出加 `sys.stdout.reconfigure(encoding="utf-8")` 防 Windows 控制台乱码。

> 实测记录：第一次下单备注乱码 → 取消订单 → 改用转义重建 → 备注正常入库。

### 2.5 鉴权
token 从 `~/.workbuddy/mcp.json` 读取，**不硬编码进任何文件**：

```json
{ "mcpServers": { "mcd-mcp": { "headers": { "Authorization": "Bearer ..." } } } }
```

## 3. 意图解析（Step 0）

模型内完成，不调工具。

| 槽位 | 示例 | 缺失时 |
|---|---|---|
| **人数** | "4个人吃" "我们仨" | **必须问**，唯一硬性缺失项 |
| 忌口 | "不吃辣" "1人吃素" "对香菜过敏" | 无则跳过 |
| 预算 | "200以内" "人均50" | 无则按人数推荐档位 |
| 场景 | 默认外送；"来店里/到店吃"→到店自取；"开车路过"→得来速 | 外送 |
| 偏好 | "要辣的" "多要点生菜" | 无则跳过 |

**原则**：人数缺失才追问，其余走默认值；**最多问一次**，一次性问全。

> 忌口原话保留，直接传给 `menu_helper.py check --restriction`。

## 4. 主流程（8 步）

### Step 1 — 定位门店

| 场景 | 调用 |
|---|---|
| 外送 | `delivery-query-addresses` → 用户选地址 → `delivery-query-stores {beType:2, addressId}` |
| 到店自取 | `query-nearby-stores {beType:1, searchType:2, city, keyword}` |
| 得来速 | `query-nearby-stores {beType:5, searchType:2, city, keyword}` |

**⚠️ 可送门店列表是动态的**（实测）：

| 时间 | 可送门店 |
|---|---|
| 10-22 21:35 | 1450056 上海食品一店、1450441 福州路、1450556 福州路上海书城 |
| 10-23 23:11 | 1450713 华旭国际大厦、1450086 新闸路、1450258 老西门地铁站 |

原门店 23:00 打烊后，`query-meals` 对其直接返回 `600057 门店可能已关闭或不在营业时间`。

**规则**：
- 每次会话**必须重新**执行 `delivery-query-stores`，不复用历史 storeCode
- 返回带 `businessStartTime` / `businessEndTime` / `businessStatus`，展示给用户
- 遇 `600057` → 重新查可送门店换一家，**不要直接告诉用户"点不了"**
- 各店在售商品数不同（实测 105 vs 102），菜单以当次 `query-meals` 为准

### Step 2 — 领券（尽早执行）

```
auto-bind-coupons {}                                    # 领取全部可领
query-my-coupons {}                                     # 取 couponId
query-store-coupons {storeCode, orderType, beType, beCode}  # 门店真实可用券
```

⚠️ 三个关键点：
1. `available-coupons` **只返回标题和图片，拿不到 couponId** —— 必须先 `auto-bind-coupons`
2. `query-my-coupons`（卡包全量）≠ `query-store-coupons`（门店可用）—— **判断能否使用一律以后者为准**
3. 券有效期短（实测 3–5 天），`tradeDateTime` 需解析，<24h 标注"今日到期"

实测：3 张券全部领取成功，但「免费脆薯饼」在三家门店均不可用。

### Step 3 — 拉菜单与套餐结构

```
query-meals {storeCode, orderType, beType, beCode}
query-meal-detail {storeCode, orderType, beType, beCode, code}
```

`query-meal-detail` 的 `rounds[]` 是搭配核心依据：

```json
{ "id": 2, "name": "选择套餐内小食", "minQuantity": 1, "maxQuantity": 1,
  "choices": [{ "code": "501205", "name": "中薯条", "quantity": 1,
                "diffPrice": "+ ¥0", "isDefault": 1 }] }
```

### Step 4 — 搭配（核心）

详见 §6。产出 `roundList`：

```json
"roundList": [
  { "round": "1", "comboItemList": [{ "code": "521952", "quantity": 1 }] },
  { "round": "2", "comboItemList": [{ "code": "501205", "quantity": 1 }] }
]
```

### Step 5 — 优惠券择优

**一次只能用一张券**（多券报 `600022`）。

**择优算法**（`menu_helper.py choose_coupon`）：
```
对每张可用券 C:
    绑定商品 = C.products[].productCode（经 canon 归一）
    若方案中未含绑定商品:
        加购成本 = 绑定商品原价（菜单查不到价格时标记 unknownAddCost，该券不可用）
    否则 加购成本 = 0
    净省(C) = 券抵扣额 - 加购成本
选净省最大者；若全部不可用则不凑单
```

⚠️ **productCode 双编码**：券绑 `1440`（麦辣鸡腿汉堡），菜单是 `901440`（麦辣鸡腿汉堡），同一商品两套编码。引擎内置 `CODE_ALIASES` 映射，否则会误判"券绑商品不在方案里"而错选券。

### Step 6 — 算价

```
calculate-price {storeCode, orderType, beType, beCode, items, needTableware, remark}
```

**金额单位是「分」**，展示除以 100。返回结构：

```json
{ "productOriginalPrice": 6690, "productPrice": 5680,
  "deliveryPrice": 600, "packingPrice": 300,
  "originalPrice": 7670, "discount": 1090, "price": 6580,
  "productList": [...] }
```

### Step 7 — 出方案，停下等确认 ⭐

呈现必须包含：商品明细表 / 配送费打包费 / **用了哪张券省了多少及到期时间** / **忌口满足情况（含未满足项及原因）** / 总价与原价对比 / 支付截止时间。

然后**停止**，等用户明确说"下单"。

### Step 8 — 下单与跟进

```
create-order {storeCode, orderType, beType, beCode, addressId, remark, needTableware, items}
query-order  {orderId}      # 用户说"支付完成"时
cancel-order {orderId, cancelReasonCode}
```

外送场景主动询问配送备注。订单 **15 分钟支付有效**（`expirePayTime`）。

## 5. 接口参考

### 5.1 枚举定义

| 枚举 | 取值 |
|---|---|
| `beType` | 1=到店自取 / 2=麦乐送 / 5=得来速 / 6=企业团餐 |
| `orderType` | 1=到店（含得来速）/ 2=外送（含麦乐送、团餐） |

| `cancelReasonCode` | 1=改主意了 / 2=重复下单 / 3=点错了 / 4=地址电话填错 / 5=送达时间选错 / -1=其它 |
| `promotionType` | 31=满额减 / 33=订单折扣（团餐） |

### 5.4 错误码

| 码 | 含义 | 处理 |
|---|---|---|
| `600022` | 暂不支持多张券使用 | 改用单券方案 |
| `600014` | 没有查询到该地址 | 换关键词/城市 |
| `600050` | 收藏餐厅列表为空 | 改用 `searchType=2` |
| `600057` | 门店可能已关闭或不在营业时间 | 重新查可送门店换一家 |
| 校验失败 `must be integer` | 整型参数被降级 | 改用脚本直连 |
| 乱码 `޽Ӵ...` | 中文未转义 | 请求体用 `ensure_ascii=True` |

### 5.5 特调（modification）规则

含 `unselectedKey` 的特调组，**组内所有项都要传**。选中用 `selectedKey`，未选中用 `unselectedKey`。

实测可用范围极窄：冰量（标准/去冰/多冰/少冰）、酱料（辣椒黄油风味酱/切块生菜）、换燕麦奶、奶油球/白砂糖。
**没有"去辣"，没有"换素食堡"，无法标注过敏原。**

## 6. 忌口策略

### 6.1 实测边界

对门店全部在售单品（102–105 款）逐一核对后确认：

| 忌口 | 支持度 | 可行方案 | 必须告知 |
|---|---|---|---|
| **吃素/素食** | ❌ 无素食主餐 | 见 §6.2 兜底库 | 「麦当劳目前没有素食主餐，只能用小食和甜品凑，主食需另行解决」 |
| **不吃辣** | ⚠️ 仅换酱料 | 改选不辣款 | 「辣味来自酱料本身，系统内无法完全去除」 |
| **不要香菜** | ⚠️ 可去 | 特调去生菜 | 「可以去掉生菜」 |
| **过敏** | ❌ 无法标注 | — | 「系统内无法标注过敏原，必须当面与门店确认」 |
| **控热量** | ✅ 支持 | 160 项营养数据 | 见 §8 |
| **无糖** | ✅ 支持 | 无糖可乐(903071)、纯牛奶(903755) | — |

### 6.4 荤素混合怎么配
- **K = 1**：1 份单人餐（R3 选 `521917`）+ 其余 N-1 人正常套餐
- **K ≥ 2**：K 人各点「单人餐 + 521917」，或 K 人各点「经典小食2件」+ 玉米杯 + 派
- **全部吃素**：只能小食 + 甜品组合，**必须在方案里明确说明主食缺失**

### 6.5 硬性规则
1. 忌口无法满足 → **必须显式说明**，不得静默替换
2. 忌口信息同时写入订单 `remark`（供门店人工确认）
3. 有荤有素混合 → 按人数拆分
4. 全部忌口都无法满足 → **先问用户**再继续
5. 甜品标注要诚实：把麦旋风当"正餐"时必须说明它是甜品
6. 辣度以酱料为准，不要因名字没有"辣"就断定不辣

## 7. 多人套餐规则

多人套餐是**固定结构 + 有限替换**，每个 round 有 `minQuantity` / `maxQuantity` 硬约束。

### 7.1 ⚠️ 人数不能靠套餐名判断

**实测反例**：

| 套餐 | 名称暗示 | 饮料数（真实人数） |

## 9. 小游戏 McDCraft

### 9.1 定位
- **形式**：单文件 HTML（`assets/mcdcraft.html`），canvas 2D，零外部依赖，离线可玩
- **风格**：麦当劳 × 我的世界 —— 体素像素风，地形用格点，色板取麦当劳品牌色（可乐棕 `#4A1B0C`、面包金 `#FAC775`、番茄红 `#E24B4A`、生菜绿 `#639922`）
- **开启**：用户说"玩一下/开始游戏"，或点完餐后提议一次
- **关闭**：说"关闭游戏/退出"或直接关页面；localStorage 存档
- **隔离**：只在 `assets/` 下，**绝不自动弹出，绝不阻塞点餐主链路**

### 9.2 玩法
| 元素 | 设计 |
|---|---|
| **主玩法** | 侧视体素平台跳跃，←→ 移动、空格跳跃、Esc 暂停 |
| **收集元素** | 可乐、汉堡、薯条、炸鸡、派、玉米杯、奶铁、麦旋风（8 种，各自像素画） |
| **敌人** | 「倒垃圾工」巡逻，撞到扣 5 分并进入 1.4s 无敌 |
| **关卡目标** | 限时收集指定组合（如 汉堡+薯条+可乐），每关递增元素种类与平台数 |
| **合成台** | 集齐 3 个相同食材合成升级版（3 薯条 → 大薯条，加分 38） |
| **计分** | 收集数 + 连击加成（combo 每 2.2s 衰减）+ 剩余时间折算 |

### 9.3 交互与存档
- 键盘：←→ 移动，空格跳跃，Esc 暂停
- `localStorage` key：`mcdcraft_save_v1`，存 `{hi, best, level}`
- 页面内始终有「退出游戏」按钮

## 12. 2026-10-24 调试修复记录

调试时用真实接口跑通全链路，发现并修复 6 个问题。

### 券有效期的认知修正（重要）

**原文档写"券有效期只有 3–5 天"，这是错的。**

| 查询时间 | 卡包券有效期 | 状态标签 |
|---|---|---|
| 2026-10-22 21:38 | 2026-10-19 10:30 ~ 2026-10-23 23:59 | 可用 |
| 2026-10-24 11:09 | 2026-10-26 10:30 ~ 2026-10-30 23:59 | **未到使用时间** |

券按**周批次滚动**：每批覆盖周一~周五 10:30–23:59，上一批过期后服务端自动换成下一批。
周末领的券通常要等到下周一才能用。已加入 `menu_helper.py coupon_state()`，
状态分 `not_started` / `usable` / `expiring` / `expired` / `unknown`。

### 修复清单

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | `auto-bind-coupons` 返回 499 被当成错误 | 服务端把"没有新券可领"用 `success:false` 返回 | `mcd_call.py` 加 `normalize_business_result()`，标记 `soft_fail` / `actionable` / `hint` |
| 2 | 券有效期解析成 `('2026','23 23:59:59')` | 用 `split("-")` 切日期，日期本身含 `-` | 改用正则匹配时间边界，同时兼容卡包券的 `tradeStartDateTime`/`tradeEndDateTime` 双字段 |
| 3 | 卡包券解析后显示"有效期未知" | `cmd_coupons` 只取 `data`（是 dict），没再取 `coupons` | 新增 `extract_coupon_list()` 兼容 4 种结构 |
| 4 | `coupons`/`check` 子命令只认 dict 格式的 plan | 未兼容 list | 新增 `extract_plan_items()` |
| 5 | 游戏：敌人坐标 NaN，敌人不动也撞不到人 | `enemies.push` 漏了 `vy:0`，`en.y += undefined` → NaN | 补初值 + 加上方边界约束 + 撞击扣 5 分 |
| 6 | 游戏：**约一半食材永远够不到** | 关卡生成有三个叠加缺陷（见下） | 改为矮台阶 + 死区修正 + 物理验证 |

### 游戏可达性问题的三层根因

这是本次调试最有价值的发现——**视觉上看着正常，实际上玩不了**。

1. **食材 y 范围过大**：原 `ri(70, groundY-TILE*2)` = 70~324，而跳跃最高只有 47px
   （初速 -7.2 / 重力 0.55 → 47px），上半屏食材完全够不到
2. **平台正下方是"死区"**：玩家站在地面会被平台挡住，跳起来撞平台底面
3. **平台可重叠**：高平台的食材被矮平台遮住

**最终方案**（`tests/reachability.test.js` 物理模拟验证 20 局 / 360 食材，0 不可达）：

| 改动 | 前 | 后 |
|---|---|---|
| 跳跃初速 | -7.2 | **-9.6**（高度 47px → 92px）|
| 重力 | 0.55 | **0.50** |
| 地面食材 y | 70~324 | **254~324**（可达线 254）|
| 平台高度 | 地面上方 0~72px | **矮台阶，离地 26~50px**（可直接走上去）|
| 平台重叠 | 允许 | **互不重叠** |
| 平台下食材 | 允许（死区） | **横向挪出平台范围** |

修复后自动试玩得分从 **79 → 516**，目标进度能真正完成。

### 13.2 新增定位选店 `scripts/locate_store.py`

**动机**：用户希望"按照定位推进"，即根据当前位置而非固定地址选店。

**接口实测约束**（决定了实现方式，很重要）：

| 约束 | 实测结果 | 影响 |
|---|---|---|
| `query-nearby-stores` 的 `keyword` | **只认地名/地址，传坐标串返回「没有查询到该地址」** | 必须先逆地理编码 |
| 门店返回的 `longitude`/`latitude` | **恒为 0.0** | 无法按坐标排序，只能靠 `distance` |
| `delivery-query-stores` 入参 | 需要 `addressId`，**无关键词入口** | 外送仍走地址列表 |

**定位链路**：坐标 →（逆地理编码）→ 地名 → `keyword` → 门店列表

逆地理编码用 Nominatim（OpenStreetMap）公共服务，无需 key。

三种入口：

```bash
python scripts/locate_store.py --city 上海市 --keyword 人民广场      # 地名
python scripts/locate_store.py --city 上海市 --locate                # 浏览器 Geolocation
python scripts/locate_store.py --city 上海市 --lat 31.2354 --lng 121.4774
```

输出 JSON：`{city, keyword, location:{lat,lng,fullAddress}, stores:[...], trace:[...]}`，
stores 已按距离升序、距离转成「227m」「1.2km」可读格式。

**实测**：关键词定位命中 5 家并正确排序；坐标定位逆出「福建中路」→ 命中最近 242m。

### 13.3 新增支付二维码 `scripts/fetch_qr.py`

**问题**：`payH5Url` 是**手机端 H5 页**，桌面端打开只显示一张二维码。把链接当纯文本贴给
用户，等于给了个用不了的东西。

**难点**：支付页是 React SPA（`<div id="root">`），静态 HTML 里只有空 div，
图片由 JS 动态插入 —— 用 curl/urllib 抓不到 `<img>`。

**方案**：Playwright 无头浏览器 + 移动端 UA + 390×844 视口渲染 → 定位面积最大的图片
（即二维码）→ clip 截图 → 输出 PNG（2 倍分辨率）。

```bash
python scripts/fetch_qr.py <orderId> [输出路径]
```

### 13.4 券的表述修正

原说法「周末领不到券」不准确。实测：

| 接口 | 返回 |
|---|---|
| `available-coupons` | 三张券 `couponStatus=HAVING_RECEIVE`、label「**已领取**」 |
| `auto-bind-coupons` | `499 暂无可领取的优惠券`（soft_fail）|
| `query-my-coupons` | 两张券在卡包，有效期 10-26~10-30，标签「未到使用时间」 |

**正确表述**：券已经领到手了，只是在卡包里；`auto-bind-coupons` 说"没有可领的"
是因为**已经领过**（同一批券不能重复领），不是周末没券。
真正的原因是**券按周批次滚动、每批覆盖周一至周五**，周末领的券要到下周一才能用。

已加入 SKILL.md Step 2，并强调要区分两种"没券"：
`available-coupons` 显示「可领取」才是真能领。

### 13.5 新增订单确认单 `scripts/order_receipt.py`

**问题**：麦当劳支付页（`payH5Url`）在桌面端只显示一张二维码，**没有任何订单明细**。
用户拿到二维码后无法确认"到底点了什么""收件人是谁""多少钱"，只能盲付。这在信任建立上是硬伤。

**方案**：下单成功后调 `query-order` 拉实时订单详情，渲染成一张可保存/可打印的 PNG 确认单。


### ⭐ 发现 1：`600057` 的真实含义被我写错了

**原文档**："600057 = 门店可能已关闭或不在营业时间" → 一律换店。

**实测**：门店 1450056 营业 06:30–23:00，**14:48 明明营业中**，

**真相**：600057 有两种成因，判据不是营业时间，而是 **beCode 与 orderType 的匹配关系**：

| 成因 | 场景 | 处理 |
|---|---|---|
| 真打烊 | 夜间 23:00 后 | 换一家店 |
| **场景错配** | 到店场景误用外送 beCode | **换回正确 beCode，不用换店** |

这个错误会导致 skill 在营业时间内无谓地换店、甚至告诉用户"点不了"。

### ⭐ 发现 2：传参组合规则与我文档描述不同

| 1（到店） | 1 / 2 / 6 | 不传 | ✅ 115 单品 |
| 1 | 1 | 任意后缀 01–08 | ✅ 115 单品 |
| 1 | 5（得来速） | 不传 | ❌ 600048 |
| 1 | 2/5/6 | 145005602 | ❌ **600057** |
| 1 | 2/5/6 | 145005601/606 | ❌ 60002 |

| 2 | **2** | **145005602** | ✅ 117 单品 |
| 2 | 1/2/5/6 | 其他后缀 | ❌ 60002 |

1. **到店（orderType=1）**：beCode 任意后缀都行，**甚至可省略**

2. **外送（orderType=2）**：**只有 beType=2 + 接口原样返回的 beCode 能通**，

4. **得来速在本店不可用** —— 配 145005602 也报 600057

配 orderType=2 一样失败。

### 15.1 ⚠️ 到店自取场景此前完全没验过（最严重）

之前只验过"到店菜单能拉通"，**从未验过到店下单**。结果一测就炸：

```

```

**根因一：漏了 `takeWayCode`**
`takeWayCode` 是 orderType=1 场景的必填项，值要从 `calculate-price` 返回的
`takeWayList[].code` 里选。我文档里完全没提这个参数。

**根因二（更隐蔽）：到店和外送是两套 productCode 体系**

| | 到店（orderType=1） | 外送（orderType=2） |
|---|---|---|
| 单品数 | 115 | 117 |
| 巨无霸 | `1100` | `901100` |
| 麦辣鸡腿堡 | `1440` | `901440` |
| 薯条 | 不在此列 | `501205` |
| 套餐示例 | `9900000888` 巨无霸四件套 | `9900003004` 麦乐鸡(5块)中套餐 |

「已售罄」，看起来像库存问题，**实际是这个商品根本不在到店菜单里**。

→ 换到店编码 `1100` + `takeWayCode` 后，**算价一次通过（26.5 元）**。

**这意味着：菜单必须按场景分别拉取，不能跨场景复用。**

## 16. 600039 是风控还是业务限额？（2026-10-24 16:05）

用户问"这个属于下单被风控了吗"。做了对照实验，**结论：不是风控，是业务侧的每日下单数上限。**

### 判定依据（5 条）

| # | 观察 | 说明 |
|---|---|---|
| 1 | 响应体只有 4 个字段 | `success/code/message/datetime/traceId`，**没有任何风控标识字段**（无 riskCode、无 verifyCode、无 captcha、无 deviceId）|
| 2 | 错误码 `600039` 属 6xxxxx 段 | 与 `600022`(多券)、`600057`(门店)、`60006`(售罄)、`600048`(缺 beCode) **同族**——都是业务校验码，不是风控码 |
| 3 | 消息文案是「今日下单数已经上限」 | 描述的是**计数状态**，不是"异常""风险""验证" |
| 4 | **只有下单被拦，其它能力全部正常** | 见下方对照表 |
| 5 | 账号信息正常无异常标记 | `query-my-account` 正常返回，积分账户无 frozen/risk 标记 |

### 对照实验：只有 create-order 被拦

| 接口 | 类型 | 结果 |
|---|---|---|
| `create-order` | 写（下单）| ❌ **600039** |
| `mall-create-order` | 写（商城下单）| ✅ 参数校验通过（400 缺参数，非 600039）|
| `delivery-create-address` | 写（建地址）| ✅ **成功**，还返回了新的 addressId |
| `draw-lottery` | 写（抽奖）| ✅ 成功 |
| `query-my-coupons` | 读 | ✅ 成功 |
| `query-nearby-stores` | 读 | ✅ 成功 |
| `mall-order-list` | 读 | ✅ 成功 |
| `query-my-account` | 读 | ✅ 成功 |

**如果是风控，通常会连账号查询、领券、活动都一起拦**（或要求二次验证）。
实际只有「餐厅下单」这一个动作被卡住，其它写操作照常成功
——甚至 `delivery-create-address` 还能新建地址，说明账号本身没有异常。

### 风控通常长什么样（对比特征，这里都不具备）

| 风控特征 | 本例是否存在 |
|---|---|
| 响应含 riskCode / verifyCode / captcha | ❌ 无 |
| 提示"请完成验证""操作频繁请稍后" | ❌ 无 |
| 账号被标记异常 / 冻结 | ❌ 无 |
| 限制多个无关业务线 | ❌ 只卡下单 |
| 需要人工审核 / 联系客服 | ❌ 无 |
| 按 IP / 设备 / 频次维度拦截 | ❌ 换店换渠道均同一结果，符合"每日 N 单"特征 |

### 最直接的证据：今天的下单时间分布

```
12:22:08  订单已取消   ← 用户自己点的
13:29:13  订单已取消   ← 我下第2单
14:53:19  订单已取消   ← 检验时
14:59:38  订单已取消   ← 检验时
15:00:18  订单已取消   ← 检验时
```

**第 5 笔创建成功、第 6 笔起开始 600039** —— 这是典型的**计数器触发**行为，
不是风控的"频次异常"模式。

### 结论与处置

- **不是风控**，是接口侧的每日下单配额（账号级，跨门店跨渠道共享）
- **取消不释放额度**（5 笔全已取消仍占满）

- 真正的教训：**接口检验时不要反复 create-order**，参数验证优先用
  `calculate-price`（不消耗额度）

已把 `api_regression.py` 改为默认不真下单（需 `--with-order` 才开）。

### ⭐ 顺带发现 2：takeWayCode 是「每家店自己的」，不能跨店复用
